# `sim/partner-bank` — the partner that demands a client certificate

A single nginx container standing in for a partner's mTLS API. It exists so the
cluster has a real counterparty to authenticate *to*: something that answers
`400 No required SSL certificate was sent` unless the caller presents a
certificate signed by the partner's CA.

| | |
| --- | --- |
| Container | `k3d-local-dev-partner-bank`, `docker.io/library/nginx:1.29-alpine` |
| Network | `k3d-local-dev`, fixed address `172.28.0.250` |
| Hostname | `api.partner-bank.test` (the server certificate's SAN) |
| Endpoint | `POST /transfers` → `200 {"status":"accepted","client":"CN=k8s-base-egress"}`; any other method → `405`; anything else → `404` |
| Keys | `.keys/local/partner-bank/` — git-ignored, generated by `make partner-sim-keys` |
| Mounts | `.keys/local/partner-bank` → `/certs:ro`, `nginx.conf` → `/etc/nginx/conf.d/default.conf:ro` |

## Why it is outside the cluster

A `partner-sim` namespace would be mesh
traffic wearing a partner's clothes: it would need a Cilium allow from
`platform-egress`, it would be reachable from any pod that could resolve its
Service, and "the credential never leaves `platform-egress`" would be a claim
about one namespace talking to another. A container on the k3d Docker network is
genuinely the `world` entity to Cilium, reached over the node's external path,
and needs no cluster-side exception at all. The only cluster object it requires
is the client credential in `platform-egress`, and the only way to it is the
egress waypoint.

The nginx image is pulled by Docker directly — it is not in `PROJECT_IMAGES` and
is not mirrored into the local registry, because nothing in the cluster pulls it.

## The three certificates

`make partner-sim-keys` is idempotent: it generates everything once and then
only re-prints the subjects.

```
.keys/local/partner-bank/
  ca.crt  ca.key      CN=partner-bank-ca  — the partner's CA, trusted by nobody else
  server.crt .key     CN=api.partner-bank.test, SAN DNS:api.partner-bank.test + IP:172.28.0.250
  client.crt .key     CN=k8s-base-egress  — what this platform presents to the partner
```

The CA is the partner's, not the platform's: it is deliberately *not* the
`local-ca` of `scripts/identity.mk`, so the trust that lets the call through is
visibly a bilateral partner relationship and not the cluster's own PKI.

`make partner-sim-inject` turns the client half into `Secret
partner-bank-client` in `platform-egress`, shaped `kubernetes.io/tls` with
`tls.crt`, `tls.key` **and** `ca.crt` — the three keys Istio's SDS reads for a
`DestinationRule` with `tls.mode: MUTUAL` and `credentialName`. It is injected by
`make` from `.keys/` exactly the way `sops-age` and `cosign-pub` are
(`scripts/teams.mk`); on a real cluster it would be a SOPS-encrypted Secret in
the platform repo, decrypted by Flux.

## Calling it by hand

From the Docker network, with the client certificate — the call the waypoint
makes:

```sh
docker run --rm --network k3d-local-dev \
  -v "$PWD/.keys/local/partner-bank:/certs:ro" \
  curlimages/curl:8.11.1 \
  -s --cacert /certs/ca.crt --cert /certs/client.crt --key /certs/client.key \
  --resolve api.partner-bank.test:443:172.28.0.250 \
  -X POST -H 'content-type: application/json' -d '{"amount":1}' \
  https://api.partner-bank.test/transfers
# {"status":"accepted","client":"CN=k8s-base-egress"}
```

Without it:

```sh
docker run --rm --network k3d-local-dev curlimages/curl:8.11.1 \
  -sk -o /dev/null -w '%{http_code}\n' -X POST https://172.28.0.250/transfers
# 400
```

`400`, not `403`: nginx refuses during the handshake, before any `location` is
reached. That is the demo's proof that the certificate lives in
`platform-egress` and not in `team-b-batch` — a team pod that tried to reach the
bank itself would get exactly this, and `kubectl -n team-b-batch get secret`
shows there is nothing it could present.

What the container saw is in its own log, which is the partner's side of the
audit trail:

```sh
docker logs k3d-local-dev-partner-bank
# 172.28.0.x "POST /transfers HTTP/1.1" 200 client="CN=k8s-base-egress" verify=SUCCESS
# 172.28.0.x "POST /transfers HTTP/1.1" 400 client="-" verify=NONE
```

## The real-world equivalent

A payment network, a clearing bank or a KYC provider that issues each client an
mTLS certificate and pins the client DN to an account. The platform-side shape
is the one that matters and is unchanged by the simulation: the workload speaks
plain HTTP to a hostname, the egress waypoint holds the credential and
originates the TLS, and because the waypoint sees plaintext the grant can be
`POST /transfers` from one ServiceAccount rather than "this namespace may open a
socket to this host". Swap `172.28.0.250` for the partner's real address and
`resolution: STATIC` for `resolution: DNS` in
`repos/team-sec-ops/edges/egress-allowlist/envs/local/api-partner-bank-test.yaml`, put the
partner-issued certificate in `partner-bank-client`, and nothing else moves.

## Validating the config without a cluster

```sh
docker run --rm -v "$PWD/sim/partner-bank/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.29-alpine nginx -t
```

`nginx.conf` here is a `conf.d` fragment, not a whole `nginx.conf`: it is the
`server` block plus the `log_format` the access line needs, and it inherits the
image's `http` context. The first sketch had it mounted at
`/etc/nginx/nginx.conf`, which would have meant restating `events`, `http` and
the default MIME types to get the same result.
